# 0.1.199 - Fix: offline calendar import, copyable warnings, startup logs, one loading screen

**Owner report:**

1. Importing a calendar in the planner shows "Import failed ... no cloud
   session, sign in first." The import should work fully offline, and the
   warning text cannot be copied.
2. No useful log of the initial load and backend contact, and two loading
   screens (a circle, then the custom one) instead of one.

## Root causes

### Calendar import needs a cloud session; its error cannot be copied

- `frontend/planner_app/lib/core/calendar.dart:27-37` (0.1.198):
  `_importCalendarFeed` threw `Calendar not imported:
  Planner.Sync.Calendar/import — no cloud session; sign in first.` whenever
  `_token` was null. Its only path was the backend POST
  `createCalendarFeed`, although the file had already been parsed in the
  browser for the preview (`modules/activity_calendar.dart`
  `_parseIcalPreview`).
- `modules/activity_calendar.dart:685-693`: the review dialog caught the
  throw and showed `SnackBar(content: Text('Import failed: $error'))`. That
  SnackBar is painted by the ScaffoldMessenger under the open dialog's modal
  barrier, so it could not be clicked, selected, or copied. Its text
  (`Import failed: Exception: ...`) also broke AGENTS.md §1.8.
- Signed out, `core/initial_data.dart` set `calendarFeeds = const []` and
  `core/planner_builders.dart` built the offline week from `DateTime.now()`
  with empty days, so even a stored feed would never have rendered, and the
  offline week ignored week navigation.
- URL subscribe (`activity_calendar.dart` `await onSubscribe(...)` without a
  catch) threw the same "no cloud session" error into the zone and left the
  dialog open with no message.
- "Still cannot be copied": the earlier fix was the page-body
  `SelectionArea` in each shell (planner `lib/app_shell.dart`, editor
  `lib/core/build_helpers.dart`, portal `lib/app_shell.dart`). SnackBars
  are painted outside that subtree and dialogs are separate routes, and the
  shared `showMessage`, `FeedbackText`, and `ConfirmWithDelayDialog`
  rendered plain `Text` with no copy action.

### No startup log; two loading screens

Line numbers are those of 0.1.198 (commit `af6e1553`).

- Two screens: `frontend/<app>_app/web/index.html:51-56` (the
  `.nc-boot-spinner` CSS rule) and `:79` (the spinner `<div>` inside
  `#nc-boot`), in all three apps, drew a CSS spinner and a centered
  "Loading Notechondria <App>..." until `flutter-first-frame`. The first
  Flutter frame then showed the shared `SplashScreen` (reaction simulator,
  title and status at the bottom right), which also faded in over 900ms.
  Measured on the 0.1.198 preview: spinner at 0-250ms, Flutter splash from
  about 1.0s, never overlapping. In addition, the shell's
  `if (_isLoading) LinearProgressIndicator` was built under the splash
  (`frontend/planner_app/lib/app_shell.dart:665`,
  `frontend/editor_app/lib/core/build_helpers.dart:477`,
  `frontend/portal_app/lib/app_shell.dart:823`), and the 10s splash timer
  (`frontend/editor_app/lib/core/bootstrap.dart:18`,
  `frontend/planner_app/lib/core/bootstrap.dart:18`,
  `frontend/portal_app/lib/core/bootstrap.dart:17`) could expire just
  before the 10s startup budget, leaving a bare progress bar between the
  splash and the banner.
- No useful log:
  `frontend/notechondria_shared/lib/src/http/http_client_internals_mixin.dart:134`
  and `:154` logged failures as `exc=${error.runtimeType}`, which release
  web builds print as `exc=minified:HJ`. The HTML-instead-of-JSON error
  (`:342`) was never logged and had no module/process.
- `verifyHandshake` called `_httpClient.get` directly, bypassing `send`
  (`frontend/planner_app/lib/core/client.dart:257`,
  `frontend/editor_app/lib/core/http_client.dart:59`,
  `frontend/portal_app/lib/core/client.dart:55`), so the first backend
  contact was neither logged nor bounded by the startup budget.
- The bootstraps only changed splash text, and editor/portal
  `_restoreSession` dropped the cause in `catch (_)`
  (`frontend/editor_app/lib/core/auth_flows.dart:187`,
  `frontend/portal_app/lib/core/bootstrap.dart:163`).

## Fix: calendar import

- New shared `parseIcalEvents` (`notechondria_shared/lib/src/utils/ical_events.dart`):
  line unfolding, VEVENT-only properties (not nested VALARM), text
  unescaping, UTC / all-day / floating and `TZID=` (read as device-local)
  times, DTEND defaults, skipped count. The review dialog and the import
  use it, so the preview count is what gets imported.
- `_importCalendarFeed` parses first. Signed in and online it keeps the
  cloud POST (same payload, including `raw_ical`). Signed out, in offline
  mode, or when the upload fails, it saves the calendar on the device
  (`core/local_calendar.dart`) in
  `notechondria.planner.local_calendar_feeds`, using the local-archive
  `calendar_feeds.json` shape plus `is_local_feed`, `source_file`, and the
  parsed `events`. Example:
  `Calendar saved on this device: Planner.Sync.Calendar/import — "Phase1
  Test Calendar" (1 event) is stored locally because you are not signed
  in; it is not uploaded to the cloud.`
- After a failed signed-in upload the same message names the cause
  (`... because the cloud upload failed (connection refused) ...`). The
  dialog still closes (the calendar was imported), but the SnackBar is
  shown as a warning for 10s instead of the 6s success message. The log
  line `Calendar saved on this device only: Planner.Sync.Calendar/push —
  cloud upload failed (<cause>).` uses the redacted
  `describeRequestFailure` cause, not the raw exception text.
- Local events are placed on the activity week (`_withLocalCalendarEvents`,
  idempotent) and listed under "Calendar this week" in the vertical board.
  The offline week now starts at the navigated week.
- Clear local data removes local calendars; `.nchron` export and restore
  carry them. Local calendars are not uploaded after a later sign-in: no
  "sync local items" path exists for calendars, so that is recorded in
  `docs/TODO.md` instead of adding new sync machinery.
- URL subscribe stays cloud-only (the server downloads the feed; a browser
  cannot fetch another site's `.ics` cross-origin, and nothing is proxied
  or CORS-loosened). Signed out it explains this inline:
  `Calendar not subscribed: Planner.Sync.Calendar/subscribe — subscribing
  by URL needs a cloud session because the server downloads the feed; this
  browser cannot fetch another site's calendar directly (cross-origin).
  Sign in, or download the .ics file and use Import iCal, which works
  offline.`
- Dialog errors stay in the dialog as copyable `FeedbackText`; the
  `Import failed: $error` SnackBar is gone. Example:
  `Calendar not imported: Planner.Sync.Calendar/parse — "empty.ics" has no
  VEVENT entries with a readable DTSTART.`

## Fix: copyable messages (all apps)

New `notechondria_shared/lib/src/components/copyable_feedback.dart`:
`CopyMessageButton` (tooltip and semantic label "Copy message"),
`copyMessageToClipboard`, and `showCopyableSnackBar` (`SelectableText`, a
Copy action, a close icon, `persist: false`, 6s or 10s for errors). They now
back `showMessage` (every app's SnackBar helper), `FeedbackText`,
`ConfirmWithDelayDialog` (Copy action), `LoadErrorBanner` (copies the
friendly text plus the raw cause), `StartupFailureView`, and the OAuth
mixin's sign-in errors. New l10n keys `feedbackCopyMessage`,
`feedbackMessageCopied`, `feedbackCopyFailed` (en + zh).

## Fix: startup log (all apps)

- `AppShellLogMixin.startupStep` writes a DEBUG "started" record and the
  outcome with its duration for each step: `local_state`, `config`,
  `handshake`, `session_restore`, `oauth_callback`, `initial_data`
  (`<App>.Startup/<step>`). A failing step logs
  `<consequence>: <App>.Startup/<step> — <cause>` and rethrows.
- `describeRequestFailure` (`notechondria_shared/lib/src/startup/startup_log.dart`)
  names the cause (`timeout after 10s (server did not respond)`,
  `connection refused`, `DNS lookup failed`, the browser's opaque network
  error, `HTML instead of JSON (HTTP 502)`, ...), drops query strings, and
  redacts `Token` / `Bearer` values.
- `send` logs `HTTP request failed: <App>.HTTP/request_failed — GET
  <host><path> after <n>ms: <cause>.` and `<App>.HTTP/slow` for startup
  requests of 3s or more. A non-JSON body is logged and thrown as
  `Server response not usable: <App>.HTTP/response — expected JSON from
  GET <url> but received HTML (HTTP 502, text/html, <n>B); check the API
  base URL and backend routing.`
- `verifyHandshake` goes through `send` and, inside a startup pass, is
  bounded only by the shared 10s budget. Its result also answers the
  version banner's first probe, so startup sends one handshake.
- `config` records the API base and why it was chosen; `session_restore`
  records `no saved session` / `saved session validated` / `kept` /
  `cleared: <cause>` (the clearing behavior is unchanged). No tokens,
  cookies, passwords, or profile data are logged.
- `initial_data` reports its real outcome: `_loadInitialData` falls back
  to local data instead of throwing, so after a fallback the step logs
  WARNING `Startup finished on local data only: <App>.Startup/initial_data
  — <cause>.` instead of `done`.
- Startup records written before the persisted log is loaded are kept, and
  the log is not saved until that merge, so startup never overwrites the
  stored history. The merge runs right after the store load, before
  anything else in `_loadLocalState` can throw. If the store load itself
  throws, `_handleBootstrapFailure` reads the stored log on its own
  (`_LocalAppStore.loadLogs`) and merges it, so a failed start and every
  Retry still persist their lines.
- The API-base check in Settings now says `API base not changed:
  <App>.Sync.Settings/save — handshake with <url> failed: <cause>.` (it
  was `Backend handshake failed for <url>: <cause>`, with no
  module/process).

## Fix: one loading surface (all apps)

- `#nc-boot` has no spinner. While loading it is a static copy of the
  splash header: same background, the app title at 8vw from the right and
  12vh from the bottom, and "Starting Notechondria <App>" below it.
- On web the `SplashScreen` header skips its intro fade, so the first
  Flutter frame matches the HTML. The splash then shows the running step
  (`Connecting to server: Planner.Startup/handshake`).
- The shell's `LinearProgressIndicator` no longer renders under the
  splash, and the splash safety timer is 12s (budget + 2s), so no bare
  progress bar appears between the splash and the banner.
- Failure states are unchanged: the HTML failed / slow message with Reload
  (Flutter never boots), the Retry / Work offline banner, and the startup
  failure view. Base href, the service-worker strip, and the 10s startup
  budget are unchanged.

## Verification

Run in `ghcr.io/cirruslabs/flutter:stable` (Flutter 3.44.0, Dart 3.12.0),
one container at a time, on a copy of `frontend/`:

- `flutter analyze`: 0 errors in all four packages. The only new issue is
  the project-wide `use_string_in_part_of_directives` info on the new
  `planner_app/lib/core/local_calendar.dart`.
- `flutter test`: editor 19, planner 14, portal 16 pass. Shared: 89 pass;
  the 3 failures in `version_update_banner_test.dart` already failed on
  `main` before this change (baseline 67 pass + the same 3).
- `smoke_test.dart` only (what CI runs): editor 5, planner 13, portal 15
  pass.
- New tests. Shared: `copyable_feedback_test.dart`, `ical_events_test.dart`,
  `startup_log_test.dart`. Planner `smoke_test.dart`: a signed-out import
  with the backend refusing connections succeeds and survives a reload; an
  empty calendar keeps the dialog open with a selectable message whose Copy
  button writes it to a mocked clipboard; signed-out subscribe explains the
  URL case inline; signed in and online, the import POSTs `raw_ical` and
  writes nothing to `local_calendar_feeds`; signed in with the upload
  refused, the calendar is stored locally, shows on the week, and the
  10s warning names `(connection refused)` while the push log line carries
  the redacted cause; a refused backend logs the `initial_data` fallback
  as a WARNING; a corrupt cached value at start still persists the
  failure lines next to the earlier history. All three `smoke_test.dart`:
  during a hanging-backend start at most one of SplashScreen /
  CircularProgressIndicator /
  LinearProgressIndicator is in the tree at any of 48 pumps 250ms apart;
  startup records with durations and `timeout after 10s` are persisted; the
  banner's Copy button copies `<App>.Startup/bootstrap`; a responsive
  backend logs `Backend reachable`, gets exactly one handshake, and the
  editor/portal session-restore outcome never contains the token.
- Pages-equivalent release builds (`--base-href /Notechondria/<app>/
  --no-web-resources-cdn --dart-define=APP_VERSION=0.1.199`) succeed. Each
  `index.html` has the base href and `#nc-boot` without a spinner, each
  `flutter_bootstrap.js` still contains `_flutter.loader.load(`, and the
  bundles' dominant version is `"0.1.199"`.

Local preview (`scripts/local_remote_deploy.sh up`, loopback only, backend
0.1.198, so the "A new version is rolling out" banner is expected), checked
with Playwright Chromium:

- Signed out, a one-event `.ics` imports, shows under "Calendar this week",
  survives a reload, and the SnackBar's Copy action copies the full
  message. The same holds with the gateway upstream black-holed
  (`REMOTE_BACKEND_ORIGIN=http://192.0.2.1`), then restored to
  `https://notechondria.trance-0.com`.
- An empty `.ics` shows the inline parse error; "Copy message" copies it
  exactly, Tab reaches the button, and Enter copies. Mouse drag-selection
  plus Ctrl+C copies the text when Flutter semantics are off; with
  semantics on, only the Copy button copies.
- Startup bursts (a screenshot every 250ms for 8s) in all three apps, live,
  with `/api/` black-holed in the page, and with the gateway black-holed:
  no spinner frame, the HTML header then the Flutter splash in the same
  place, the banner after about 10s when black-holed, and exactly one
  handshake request per start. The logs show every step with its duration
  and causes such as `timeout after 10s (server did not respond)`; the
  `initial_data` outcome is `every cloud request answered` live and a
  WARNING `Startup finished on local data only: ...` when black-holed.
- A refused upstream (`http://127.0.0.1:9`, gateway HTML 502) now shows
  `Cloud data not loaded: Planner.HTTP/response — the server returned an
  error (HTTP 5xx). Retry in a moment or work offline.` and the handshake
  log names `Handshake got HTML instead of JSON ... (HTTP 502)`.
- With `flutter_bootstrap.js` blocked, `#nc-boot` shows its
  "could not start" message and Reload.

Not run: CI itself (runs after the owner pushes), Firefox, Safari,
iOS/Android installs, the real Pages deploy, and a screen reader. Docker on
the dev host discards `--memory` and rejects `--cpus`, so container caps
were not enforced; runs used `timeout` and ran one at a time.
