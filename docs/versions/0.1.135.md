# 0.1.135 - MCP → standalone CLI migration proposal

## User request

Considering migrating MCP to a CLI app — propose the migration.

## What changed

Documentation-only. Authored
[`docs/integrations/mcp-cli-migration.md`](../integrations/mcp-cli-migration.md):
a phased proposal to move the MCP server out of the Django backend into
a standalone CLI app that talks to the backend over the public
`/api/v1/` surface with the existing `Bearer ntc_<key>` auth.

Highlights:

- **Why:** the in-backend `/mcp/` tools call the Django ORM directly
  ([`backend/mcp/tools.py`](../../backend/mcp/tools.py)), so MCP can
  only run where the full backend runs — no distributable/self-hosted
  story, coupled release cadence, and doc drift.
- **Target:** a `notechondria-mcp` CLI (recommended Python, using the
  official `mcp` SDK) whose tool handlers map MCP calls to `/api/v1/`
  requests. Backend stays the source of truth + API + skill.md.
- **Auth unchanged:** ntc_ key minted in Settings, pasted into CLI
  config, sent as `Bearer ntc_<key>`.
- **Backend changes (additive, non-breaking):** expose `mcp_skill_md`
  over the API (`GET /api/v1/auth/mcp-skill/`), audit that `/api/v1/`
  covers every tool operation, confirm CORS, treat `/api/v1/` as a
  stable contract. No DB migration.
- **5 phases:** API gap audit → CLI skeleton → full tool parity →
  distribute (PyPI) → cutover + delete `backend/mcp/`.
- Records open questions for the owner (separate repo vs `cli/`,
  Python vs TypeScript, keep `/mcp/` hosted or fully cut over) and
  flags the stale auth-header example in `docs/server/mcp.md` to fix
  in Phase 1.
