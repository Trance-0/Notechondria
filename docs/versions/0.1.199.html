Notechondria Documentation

0.1.199 - Fix: offline calendar import, copyable warnings, startup logs, one loading screen

Owner report:

  1. Importing a calendar in the planner shows "Import failed ... no cloud session, sign in first." The import should work fully offline, and the warning text cannot be copied.
  2. No useful log of the initial load and backend contact, and two loading screens (a circle, then the custom one) instead of one.

Root causes

Calendar import needs a cloud session; its error cannot be copied

  • frontend/planner_app/lib/core/calendar.dart:27-37 (0.1.198): _importCalendarFeed threw Calendar not imported: Planner.Sync.Calendar/import — no cloud session; sign in first. whenever _token was null. Its only path was the backend POST createCalendarFeed, although the file had already been parsed in the browser for the preview (modules/activity_calendar.dart _parseIcalPreview).
  • modules/activity_calendar.dart:685-693: the review dialog caught the throw and showed SnackBar(content: Text('Import failed: $error')). That SnackBar is painted by the ScaffoldMessenger under the open dialog's modal barrier, so it could not be clicked, selected, or copied. Its text (Import failed: Exception: ...) also broke AGENTS.md §1.8.
  • Signed out, core/initial_data.dart set calendarFeeds = const [] and core/planner_builders.dart built the offline week from DateTime.now() with empty days, so even a stored feed would never have rendered, and the offline week ignored week navigation.
  • URL subscribe (activity_calendar.dart await onSubscribe(...) without a catch) threw the same "no cloud session" error into the zone and left the dialog open with no message.
  • "Still cannot be copied": the earlier fix was the page-body SelectionArea in each shell (planner lib/app_shell.dart, editor lib/core/build_helpers.dart, portal lib/app_shell.dart). SnackBars are painted outside that subtree and dialogs are separate routes, and the shared showMessage, FeedbackText, and ConfirmWithDelayDialog rendered plain Text with no copy action.

No startup log; two loading screens

Line numbers are those of 0.1.198 (commit af6e1553).

  • Two screens: frontend/<app>_app/web/index.html:51-56 (the .nc-boot-spinner CSS rule) and :79 (the spinner <div> inside #nc-boot), in all three apps, drew a CSS spinner and a centered "Loading Notechondria ..." until flutter-first-frame. The first Flutter frame then showed the shared SplashScreen (reaction simulator, title and status at the bottom right), which also faded in over 900ms. Measured on the 0.1.198 preview: spinner at 0-250ms, Flutter splash from about 1.0s, never overlapping. In addition, the shell's if (_isLoading) LinearProgressIndicator was built under the splash (frontend/planner_app/lib/app_shell.dart:665, frontend/editor_app/lib/core/build_helpers.dart:477, frontend/portal_app/lib/app_shell.dart:823), and the 10s splash timer (frontend/editor_app/lib/core/bootstrap.dart:18, frontend/planner_app/lib/core/bootstrap.dart:18, frontend/portal_app/lib/core/bootstrap.dart:17) could expire just before the 10s startup budget, leaving a bare progress bar between the splash and the banner.
  • No useful log: frontend/notechondria_shared/lib/src/http/http_client_internals_mixin.dart:134 and :154 logged failures as exc=${error.runtimeType}, which release web builds print as exc=minified:HJ. The HTML-instead-of-JSON error (:342) was never logged and had no module/process.
  • verifyHandshake called _httpClient.get directly, bypassing send (frontend/planner_app/lib/core/client.dart:257, frontend/editor_app/lib/core/http_client.dart:59, frontend/portal_app/lib/core/client.dart:55), so the first backend contact was neither logged nor bounded by the startup budget.
  • The bootstraps only changed splash text, and editor/portal _restoreSession dropped the cause in catch (_) (frontend/editor_app/lib/core/auth_flows.dart:187, frontend/portal_app/lib/core/bootstrap.dart:163).

Fix: calendar import

  • New shared parseIcalEvents (notechondria_shared/lib/src/utils/ical_events.dart): line unfolding, VEVENT-only properties (not nested VALARM), text unescaping, UTC / all-day / floating and TZID= (read as device-local) times, DTEND defaults, skipped count. The review dialog and the import use it, so the preview count is what gets imported.
  • _importCalendarFeed parses first. Signed in and online it keeps the cloud POST (same payload, including raw_ical). Signed out, in offline mode, or when the upload fails, it saves the calendar on the device (core/local_calendar.dart) in notechondria.planner.local_calendar_feeds, using the local-archive calendar_feeds.json shape plus is_local_feed, source_file, and the parsed events. Example: Calendar saved on this device: Planner.Sync.Calendar/import — "Phase1 Test Calendar" (1 event) is stored locally because you are not signed in; it is not uploaded to the cloud.
  • After a failed signed-in upload the same message names the cause (... because the cloud upload failed (connection refused) ...). The dialog still closes (the calendar was imported), but the SnackBar is shown as a warning for 10s instead of the 6s success message. The log line Calendar saved on this device only: Planner.Sync.Calendar/push — cloud upload failed (<cause>). uses the redacted describeRequestFailure cause, not the raw exception text.
  • Local events are placed on the activity week (_withLocalCalendarEvents, idempotent) and listed under "Calendar this week" in the vertical board. The offline week now starts at the navigated week.
  • Clear local data removes local calendars; .nchron export and restore carry them. Local calendars are not uploaded after a later sign-in: no "sync local items" path exists for calendars, so that is recorded in docs/TODO.md instead of adding new sync machinery.
  • URL subscribe stays cloud-only (the server downloads the feed; a browser cannot fetch another site's .ics cross-origin, and nothing is proxied or CORS-loosened). Signed out it explains this inline: Calendar not subscribed: Planner.Sync.Calendar/subscribe — subscribing by URL needs a cloud session because the server downloads the feed; this browser cannot fetch another site's calendar directly (cross-origin). Sign in, or download the .ics file and use Import iCal, which works offline.
  • Signed in, a URL subscribe whose create POST succeeded but whose follow-up refresh failed returned Calendar not subscribed: Planner.Sync.Calendar/subscribe — <cause>. and kept the dialog open, so a retry registered a duplicate server-side feed (core/calendar.dart _subscribeCalendarFeed wrapped createCalendarFeed and _refreshCalendarState in one try). The refresh failure is now handled on its own, as _importCalendarFeed does: it logs Calendar list not refreshed: Planner.Sync.Calendar/refresh — <cause>; the subscription itself succeeded. and the dialog closes with the success message. A planner smoke_test.dart case checks one create call and a closed dialog (planner tests: 15 pass; analyze: 0 errors).
  • Dialog errors stay in the dialog as copyable FeedbackText; the Import failed: $error SnackBar is gone. Example: Calendar not imported: Planner.Sync.Calendar/parse — "empty.ics" has no VEVENT entries with a readable DTSTART.

Fix: copyable messages (all apps)

New notechondria_shared/lib/src/components/copyable_feedback.dart: CopyMessageButton (tooltip and semantic label "Copy message"), copyMessageToClipboard, and showCopyableSnackBar (SelectableText, a Copy action, a close icon, persist: false, 6s or 10s for errors). They now back showMessage (every app's SnackBar helper), FeedbackText, ConfirmWithDelayDialog (Copy action), LoadErrorBanner (copies the friendly text plus the raw cause), StartupFailureView, and the OAuth mixin's sign-in errors. New l10n keys feedbackCopyMessage, feedbackMessageCopied, feedbackCopyFailed (en + zh).

Fix: startup log (all apps)

  • AppShellLogMixin.startupStep writes a DEBUG "started" record and the outcome with its duration for each step: local_state, config, handshake, session_restore, oauth_callback, initial_data (<App>.Startup/<step>). A failing step logs <consequence>: <App>.Startup/<step> — <cause> and rethrows.
  • describeRequestFailure (notechondria_shared/lib/src/startup/startup_log.dart) names the cause (timeout after 10s (server did not respond), connection refused, DNS lookup failed, the browser's opaque network error, HTML instead of JSON (HTTP 502), ...), drops query strings, and redacts Token / Bearer values.
  • send logs HTTP request failed: <App>.HTTP/request_failed — GET <host><path> after <n>ms: <cause>. and <App>.HTTP/slow for startup requests of 3s or more. A non-JSON body is logged and thrown as Server response not usable: <App>.HTTP/response — expected JSON from GET <url> but received HTML (HTTP 502, text/html, <n>B); check the API base URL and backend routing.
  • verifyHandshake goes through send and, inside a startup pass, is bounded only by the shared 10s budget. Its result also answers the version banner's first probe, so startup sends one handshake.
  • config records the API base and why it was chosen; session_restore records no saved session / saved session validated / kept / cleared: <cause> (the clearing behavior is unchanged). No tokens, cookies, passwords, or profile data are logged.
  • initial_data reports its real outcome: _loadInitialData falls back to local data instead of throwing, so after a fallback the step logs WARNING Startup finished on local data only: <App>.Startup/initial_data — <cause>. instead of done.
  • Startup records written before the persisted log is loaded are kept, and the log is not saved until that merge, so startup never overwrites the stored history. The merge runs right after the store load, before anything else in _loadLocalState can throw. If the store load itself throws, _handleBootstrapFailure reads the stored log on its own (_LocalAppStore.loadLogs) and merges it, so a failed start and every Retry still persist their lines.
  • The API-base check in Settings now says API base not changed: <App>.Sync.Settings/save — handshake with <url> failed: <cause>. (it was Backend handshake failed for <url>: <cause>, with no module/process).

Fix: one loading surface (all apps)

  • #nc-boot has no spinner. While loading it is a static copy of the splash header: same background, the app title at 8vw from the right and 12vh from the bottom, and "Starting Notechondria " below it.
  • On web the SplashScreen header skips its intro fade, so the first Flutter frame matches the HTML. The splash then shows the running step (Connecting to server: Planner.Startup/handshake).
  • The shell's LinearProgressIndicator no longer renders under the splash, and the splash safety timer is 12s (budget + 2s), so no bare progress bar appears between the splash and the banner.
  • Failure states are unchanged: the HTML failed / slow message with Reload (Flutter never boots), the Retry / Work offline banner, and the startup failure view. Base href, the service-worker strip, and the 10s startup budget are unchanged.
