# 0.1.176 - Fix: course sync as ONE atomic commit (Git Data API)

## Context

Found while running the real Veronica-7 migration end-to-end against
production (step 2 + 3). Import worked perfectly — 193 notes, 6 modules,
0 warnings, idempotent on re-import — but the **first sync of the 193-note
course 503'd after 120 s**, and the fork showed a flood of ~70 partial
`notechondria: sync …` commits before the worker was killed. The push was
non-atomic and never completed.

## Root cause

`courses/git_service._commit_files` (0.1.174) wrote each file with a
separate **Contents API** `PUT` — i.e. **one commit per file**. For a
193-file course that is ~386 sequential GitHub round-trips inside a single
HTTP request: it exceeded the gateway timeout (503 to the client), the
worker was terminated mid-loop (partial, non-atomic push, `git_pending_since`
left set with no `git_last_sync_error`), and it polluted the repo history
with hundreds of one-file commits.

## Fix

`_commit_files` now pushes **all mapped files in one commit via the Git
Data API**, a fixed handful of calls regardless of file count:

1. `GET git/ref/heads/<branch>` → base commit sha
2. `GET git/commits/<sha>` → base tree sha
3. `POST git/trees` with `base_tree` + every file as a `blob` entry
   (unmanaged files — `.vitepress/**`, code, CI — stay from the base tree)
4. **short-circuit**: if the new tree sha equals the base tree sha, the
   recomposed markdown is byte-identical → return without creating an
   empty commit
5. `POST git/commits` (single commit) → `PATCH git/refs/heads/<branch>`

Atomic (all-or-nothing), fast (well within the request timeout), and one
clean commit. Structured `CourseGitServiceError` on any step's failure so
`sync_course_to_repo` records `git_last_sync_error` and re-raises.

Also: **`git_path` is now exposed on `NoteDetailSerializer`** (read-only)
so the owner/agent can inspect a git-imported note's repo mapping — it was
persisted correctly (proven by idempotent re-import) but invisible over
the API.
