# 0.1.164 - Recurring events (backend + MCP/CLI), course git-binding data model

## Context

This round opens a large owner request spanning event recurrence,
activity-UI fixes, a full course↔GitHub binding feature with lazy
sync, an app-wide developer menu, and MCP/CLI parity for remote
agents. It is delivered in CI-verified increments. This first
increment lands the **backend data-model foundation** that the rest
builds on, because the backend has real CI test signal
(`backend-tests.yml`) whereas the Flutter apps do not run locally on
this host (see AGENTS.md host budget). The remaining scope is captured
in `docs/TODO.md` under "GitHub course binding & activity UX".

## What changed

### Recurring planner events (backend)

`PlannerEvent` gained a recurrence **rule stored on the single base
row** (no per-occurrence materialisation):

- `recurrence_freq` — `N` does-not-repeat (default), `W` weekly, `M`
  monthly, `Y` yearly.
- `recurrence_interval` — every N periods (default 1).
- `recurrence_end_date` — inclusive last date the series may occur.
- `recurrence_count` — total occurrences including the first.

Migration `planner/0004_plannerevent_recurrence.py` (additive; the four
fields all have defaults / are nullable, so it is safe on the live DB).

`calendar_week_payload` (`notes/services.py`) now **expands** the
series into the requested window:

- New helpers `_add_months` (day-clamping, leap-safe), `_add_period`,
  `_expand_occurrence_dates` (honours end-date and count, guarded by a
  4000-occurrence ceiling), and `_occurrence_payload` (shifts
  `starts_at`/`ends_at` by the day delta so the time-of-day is
  preserved and tags `occurrence_date`).
- The grid query now selects one-time events inside the window **plus
  every recurring series** (its base may predate the window) and
  expands each. Recurring series contribute their single next upcoming
  occurrence (400-day horizon) to the deadlines/urgency list so a
  weekly class does not flood it.

`planner_event_payload` exposes the four recurrence fields;
`PlannerEventWriteSerializer` accepts them (choice/int/date validation);
the list-create and detail-patch views persist them.

### Course git-binding data model (foundation only)

`Course` gained additive git fields (migration
`courses/0006_course_git_binding.py`): `git_provider`, `git_repo`
(`owner/name`, empty = unbound), `git_branch`, `git_sync_enabled`,
`git_sync_timeout_minutes` (owner-tunable lazy-commit debounce,
default 5), `git_pending_since`, `git_last_synced_at`,
`git_last_sync_error`. **No new model type** was introduced, per the
owner requirement. Import/bind/unlink endpoints, the lazy-sync worker,
effective logging, the repo selector UI, and MCP/CLI course-git tools
are tracked in TODO for the next increments.

### MCP / CLI parity

`create_event` and `update_event` in both `backend/mcp/tools.py` and
`cli/notechondria_mcp/tools.py` accept the four recurrence params, and
`_event_payload` returns them, so remote agents can create and read
recurring events. Schemas document the `N/W/M/Y` enum and the
end-date-OR-count contract.
