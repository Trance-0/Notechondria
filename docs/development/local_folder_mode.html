Status: Phase 1 (foundation, section 9.1) is implemented in 0.1.200: the storage core, transport, router, Phase 1 handlers, and widgets under frontend/notechondria_shared/lib/src/. Owner request (intent): add an option in the login window that checks for a qualified Chrome; if qualified, use a local folder as a pure local file backend; support all features; the frontend reads and renders content locally and acts only as a dashboard for local services.

Summary

  • Qualification is feature detection (showDirectoryPicker, isSecureContext, permission and iteration methods, Web Locks, not mobile). Brands from navigator.userAgentData are only a label. Native builds hide the option.
  • Architecture: option A. A shared, in-page local backend implements the /api/v1 routes the apps already call. It plugs in as the http.Client that HttpClientInternalsMixin.send operations call, so existing app code paths run unchanged against a folder. While an app is in folder mode, every request through its client is answered in the page. Routing follows the app's storage mode, not the request host or the folder's permission state, and the mode is decided synchronously before the first request (2.8).
  • Folder layout extends the GitHub data-sync layout (backend/creators/services/github_sync.py:11-28): one .md file plus a .meta.json sidecar per note, JSON for everything else, attachments as real files, and a manifest.json with a layout version. A .nchron export carries both the v1 buckets and a verbatim copy of the folder.
  • Multi-tab safety: every write re-reads its files from disk under an exclusive Web Lock, multi-file writes go through a journal, and reads take the lock in shared mode (6.2).
  • Feature matrix (section 4): 44 features work fully locally (a), 5 work by calling a third party from the browser (b), 13 need a server (c). One listed area (AI/LLM) has no feature today and is not counted.
  • Main risk: the Pages origin https://trance-0.github.io is shared with other Trance-0 Pages projects (section 6.1). Same-origin code can reach a granted folder. v1 therefore passes no folder handle between tabs on any origin; each app tab opens the folder itself (6.2). A dedicated origin removes the other projects, but the loopback preview and the Docker self-host still serve uploaded /media/ files on the app origin (6.1).

Gesture order, so that each browser call that needs transient activation is the first call of its own click handler:

  1. If the shared-origin notice (6.1 mitigation 2) has not been acknowledged on this browser (notechondria.shared.local_folder_notice_ack), the option's onPressed only opens the notice dialog. The dialog holds the "Remember this folder on this browser" checkbox (6.1 mitigation 1) and a "Choose folder" button. That button's onPressed calls showDirectoryPicker before any await.
  2. Once the notice is acknowledged (and on origins that need none), the option's onPressed calls showDirectoryPicker first. Every directory picker in the app passes {id: 'notechondria-folder', mode: 'readwrite'}, so a later "Choose '' again" opens where the folder was chosen (MDN id option).
  3. When the picked folder is empty, the app shows "Start empty" and "Start from an archive". "Start from an archive" opens the .nchron file picker as the first call of its own onPressed. The file picker is never chained after the directory picker within one gesture.
  4. The reconnect view (2.9, 6.3) has two buttons, and each one's browser call is the first call of its onPressed:
    • "Reconnect ''", shown when a handle exists and its grant expired, calls requestPermission({mode: 'readwrite'});
    • "Choose '' again", shown when there is no handle (session-only mode after every reload and in every new tab), calls showDirectoryPicker({id: 'notechondria-folder', mode: 'readwrite'}). Only after the picker returns does the app read the picked folder's manifest.json and check its folder_id (2.9).

T3: on origins without the notice, the "Remember this folder on this browser" checkbox sits in the pick flow and in the status card, unchecked by default (2.10). "Use the connected folder ''" takes the Reconnect path when a remembered handle exists and the "Choose again" path otherwise, with its folder_id checks and the 2.10 rule 3 push.

Messages for unqualified browsers (AGENTS.md 1.8 shape; module rows in 9.4):

  • noDirectoryPicker: "Local folder mode unavailable: Shared.LocalFolder/qualify — this browser does not provide window.showDirectoryPicker (File System Access API). Firefox and Safari do not offer it."
  • insecureContext: "Local folder mode unavailable: Shared.LocalFolder/qualify — the page is not a secure context (window.isSecureContext is false). Open the app over https or from http://127.0.0.1."
  • noPermissionApi / noDirectoryIteration: "Local folder mode unavailable: Shared.LocalFolder/qualify — this browser exposes the folder picker but not FileSystemHandle.requestPermission (or directory iteration), so a folder could not be reopened or scanned."
  • noWebLocks: "Local folder mode unavailable: Shared.LocalFolder/qualify — navigator.locks (Web Locks API) is missing, so two tabs could corrupt the folder."
  • mobile: "Local folder mode unavailable: Shared.LocalFolder/qualify — a mobile browser was detected (navigator.userAgentData.mobile, or the user agent when that is missing). Folder mode is desktop-only in this release."

Fallback line, shown under every message: "Keep working signed out in browser-local mode and back up with the local-data export (.nchron), or use the Notechondria desktop build." The desktop build exists for the portal only (.github/workflows/portal-release.yml:131-156), and it stores data through shared_preferences, not in a folder (folder mode for it is Q11).

2.2 Options

  • A. Route-level local backend (chosen). A shared LocalFolderTransport extends http.BaseClient decodes each request (JSON or http.MultipartRequest), dispatches (method, path) to handlers that implement the /api/v1 contract over the folder, and returns JSON responses with the backend's shapes and status codes.
  • B. Storage adapter under each app's local store. Keep the apps in signed-out or offline mode and replace the SharedPreferences backing of each _LocalAppStore (for example frontend/editor_app/lib/core/local_store.dart:33-139) and AppShellLocalPersistMixin (frontend/notechondria_shared/lib/src/app_shell/app_shell_local_persist_mixin.dart:46-92) with folder files.
  • A'. Dart-interface variant of A: implement each app's NotechondriaClient directly (frontend/editor_app/lib/core/client.dart:6, frontend/planner_app/lib/core/client.dart:4, frontend/portal_app/lib/core/client_base.dart:4). Rejected: the three interfaces differ, so this needs three implementations, and it skips the HTTP logging and decode path.
  • C. Host the local backend in a SharedWorker so one process serves all tabs. Rejected for v1: it needs a separate dart2js entrypoint and a shared script path in the Pages tree (a CI change). Web Locks give the needed write serialization without it.
  • D. A localhost daemon speaking /api/v1. Not designed here (no network listener by default); see section 2.6 and Q1.

2.4 Decision

Choose A. It is the only option that reaches every storage-backed feature without rewriting three apps' offline branches, it has a single place to enforce locking and atomic writes, and it can be tested in the VM with the injection the smoke tests already use. The cost is contract drift, which section 8.4 contains with recorded response fixtures. Design review 1 did not find A unsound; its routing finding (H1) is fixed in 2.8.

2.5 Components and request flow

New shared module frontend/notechondria_shared/lib/src/local_folder/:

  • FolderFs: a small interface (readText, readBytes, writeText, writeBytes, list, stat, remove). Implementations: the web File System Access backend, an in-memory fake for tests, and a stub for non-web builds.
  • LocalFolderController (a ChangeNotifier): the app's storage mode (browserOrCloud or folder, decided before the first request, 2.8) and, separately, the folder state (opening, needsPick, needsPermission, scanning, active, error, disconnected). It owns the handle, the permission checks, the in-memory index (a read cache only, 6.2 R2), the lock, the change channel, and the app's StorageModeClient (httpClient, created on first use over http.Client()).

    • Owner. There is one controller per app instance. _NotechondriaAppState creates it as a late final field next to _client (editor app_shell.dart:52-53, planner :38-39, portal :38-39) and passes it to AppShell and, in the portal, to _NoteRoutePage (frontend/portal_app/lib/components/note_route_page.dart:11-23), which uses the client outside any AppShell. AppShell does not create it: the client is built before any shell exists, and the portal builds one shell per route (portal app_shell.dart:92-105, :161). Wiring is in 2.7.

    • Zone binding. The controller is created during the root widget's first build, inside runGuardedApp's zone and before _bootstrapApp enters a startup budget, and captures Zone.current then. package:web does not bind callbacks to a zone (1.4), so every Dart function passed to JavaScript is bound before .toJS. The wrapper depends on what JavaScript does with the return value (table in 9.2):

      • Void listeners (BroadcastChannel messages, FileSystemObserver, focus, visibilitychange) use the captured zone's bindUnaryCallbackGuarded (bindBinaryCallbackGuarded for the observer's two arguments). An exception then reaches runGuardedApp's handler, and a refresh fired later never runs inside a startup budget.
      • The locks.request callback must return the operation's promise. The browser holds the lock until that promise settles, and when the callback returns a non-promise it releases the lock "in an upcoming microtask" (Web Locks spec, section 2.4 note). A guarded wrapper returns void Function(T) (api.dart.dev), which JavaScript sees as undefined, so it would release every lock before the operation's first await, and the bug would compile silently. The callback is therefore bound with the non-guarded Zone.current.bindUnaryCallback<JSPromise<JSAny?>, Lock?>, in the zone of the request that asked for the lock, because it continues that request. Its body runs the operation inside a try/catch, completes the caller's Completer with the result or the error, and returns that block's Future<void> as .toJS. The promise therefore always resolves, and the lock is released exactly when the operation ends.
      • Lock-wait timeouts use AbortSignal.timeout(ms) (bound in package:web 1.1.1), which takes no Dart callback.

      Chromium tests for the lock wrapper are in 8.3; the VM fakes cannot show this bug.

  • LocalFolderTransport extends http.BaseClient: request decode, the folder lock (shared for GET, exclusive otherwise, 6.2 R1), dispatch, response encode. Responses carry content-type: application/json and x-notechondria-backend: local-folder. While the folder state is opening it holds requests; outside active it answers 503 (2.8 rule 4). Deadlines run from request start (2.9).
  • LocalBackendRouter and handlers per area (notes, trash, courses, planner, calendar, attachments, settings and auth, GitHub).
  • StorageModeClient extends http.BaseClient: routes by storage mode (2.8). The (b) handlers make their third-party calls (GitHub, calendar URLs) through a separate plain http.Client owned by the transport.

Flow: UI action, app method (for example createNote), _post, send() (logging), _httpClient.post, StorageModeClient, LocalFolderTransport, router, handler, FolderFs, JSON response, decode(), back to the unchanged app code.

Unsupported routes (class (c), section 4) answer HTTP 501 with {"detail": "<section 1.8 message>"}. Folder errors use 501 (unsupported) or 503 (folder unavailable) and never 401 or 403. The transport ignores the Authorization value, because the folder has one user, so no route answers 401. Every detail contains "—", so shapedErrorMessage passes it through verbatim (http_client_internals_mixin.dart:320-321). No detail may contain any of the four substrings the session-rejection detectors count:

  • the three docs/AGENTS.md sentinels, invalid token, authentication credentials were not provided, and token_not_valid;
  • session rejected:, which shapedErrorMessage prefixes onto every 401 body without an em-dash (:323-324).

The detectors are editor frontend/editor_app/lib/core/initial_data.dart:279-290, planner frontend/planner_app/lib/core/initial_data.dart:261-267, and portal frontend/portal_app/lib/core/initial_data.dart:269-275. Two hits in one load clear the session, so a stray 401 in folder mode would sign the user out. A unit test checks every folder detail string against the four substrings. Details also interpolate folder names and browser error text, which could contain one (a folder named "Invalid token"), so every assembled detail goes through scrubSessionSentinels, which puts a zero-width word joiner (U+2060) after the first letter of each match; the text reads the same. It folds each character with toLowerCase, as the detectors do. The router's 501 and 404 details interpolate the request path, so they go through scrubRouteDetail, which also breaks the editor's deep-link markers (permission, forbidden, not authenticated, 403, 403:; design review 3 T2).

2.6 How "dashboard for local services" is met

The local backend is the service. It owns IDs, validation, trash, history, recurrence expansion, search ranking, and activity aggregation, which are the same responsibilities the Django backend has. The UI keeps calling the same /api/v1 contract and only reads and renders responses.

In folder mode no note, course, planner, profile, or settings data goes to the Notechondria server: every request through the app's HTTP client is answered in the page (2.8). The requests that still leave the page carry no folder data: the manual "Check for updates" handshake (2.8 rule 3); the browser's own loads of absolute https image URLs that a note body or an adopted profile already contains (F32); and the portal's startup image when the user set it to a remote URL, a per-device preference (frontend/portal_app/lib/components/custom_splash_overlay.dart:67-79, F63). Class (b) calls go straight to the named third party (GitHub, a calendar host).

The service lives inside each app's page rather than in a separate process. Because it speaks the backend contract, the same router could later run in a localhost daemon or in the desktop build, with the UI pointed at it through the existing API base URL setting. Whether the owner meant such a separate process is open question Q1. This design does not open any network listener.

3.3 Interchange with .nchron (export format v1) and GitHub sync

The v1 archive is a dump of _LocalAppStore buckets (docs/export_format_v1.md:8-29; writer frontend/notechondria_shared/lib/src/utils/local_archive.dart:135-246). The folder is shaped like the server data instead. Two rules make them interchangeable:

  1. Folder to .nchron. The export writes the normal v1 bucket files, derived from the folder (drafts.json holds every live note as a local draft with client_draft_id = fld_<uuid-hex>, courses.json the courses, planner_events.json and calendar_feeds.json the planner data, attachments/<client-id>/<file> the bytes). It also adds an optional folder/ subtree with a verbatim copy of the folder, minus .notechondria/ and *.crswap. readLocalArchive builds a name map and looks up only known entries (local_archive.dart:273-275), so v1 readers ignore folder/, and docs/export_format_v1.md:39-43 allows extra optional files without a version bump (decision D3). The copy repeats attachment bytes that the v1 attachments/ entries already hold, so attachment-heavy archives are about twice as large.
  2. .nchron to folder. If folder/ is present, restore it verbatim into an empty folder (lossless round trip), with one exception: the restore writes a new folder_id and keeps the original as restored_from_folder_id. A restored folder therefore never shares a lock name or a remembered-handle key with its source (3.7). Otherwise map buckets to records the way the post-login push does (section 7.1). Either way the import runs in chunks and writes manifest.json last (6.2 R4).

So folder, zip, folder is lossless; browser-local, zip, folder keeps everything browser-local mode has; folder, zip, browser-local keeps notes, courses, and planner data but drops history and sessions, which browser-local mode does not model. Attachments on that last path are U16: the base64-to-LocalAttachmentStore move runs once per browser (frontend/editor_app/lib/core/local_persist.dart:51-55), so imported bytes may stay in the localStorage drafts bucket.

Because the folder is a superset of the GitHub data-sync layout, a cloned data-sync repository can be opened as a folder (Phase 4 "adopt" action, ID rules in 3.7), and the folder can be pushed to GitHub with the same layout (feature F49).

Two doc-versus-code differences in docs/export_format_v1.md should be fixed when the bridge lands: the collision suffix is __$i in code (local_archive.dart:179) but -<index> in the doc (:96), and the doc says import first wipes local state (:151-152) while the editor import only replaces six buckets (frontend/editor_app/lib/core/local_archive_io.dart:178-200).

5. Secrets

  • Credentials are never written to the folder, to a .nchron export, or to logs. The folder may sit in a cloud-synced directory, and an archive is a file users share. local_archive.dart strips nothing itself; its comment makes stripping the caller's job (local_archive.dart:67-68).
  • The folder bridge (9.2) applies a key denylist to every JSON object it exports (the v1 buckets and the folder/ copy), to the GitHub push, and to every write under profile/. Matching rule: keys are compared case-insensitively as whole keys, never as substrings.
    • Stripped: the exact keys token, pat, secret, password, passphrase, authorization, cookie, credential, credentials, api_key, and apikey, and any key ending in _token, _secret, _password, or _key. The suffixes cover access_token, refresh_token, github_token, client_secret, and private_key.
    • Exempt: path and any key ending in _path. .nchron attachment pointers use path (local_archive.dart:350-355), and app data also uses source_path and git_path.
    • Test, both directions: a fixture with every key the bridge writes today plus the stripped list, nested at several depths. Every stripped key must be gone, and path, source_path, git_path, patch, pattern, tokens_used, and keyboard_layout must survive. A new benign key that ends in _key fails the test and must be added to an explicit exempt list.
  • The only (b) features that need a credential are F49, F51, and F52, which use a GitHub fine-grained personal access token. F32 and F42 need none. F55 does not exist; a future LLM key would use the same store.
  • How the user supplies it: in folder mode the GitHub card shows a token field and a link to GitHub's fine-grained token page, with the scope the App uses today (one repository, Contents read and write, Metadata read; docs/integrations/github-sync.md:33-37). The token is checked with one GET https://api.github.com/user before it is kept. Log lines name the outcome and never the token, its prefix, or its length:

    • "GitHub token not stored: Shared.LocalFolder.GitHub/token — GET https://api.github.com/user answered ."
    • "GitHub push unavailable: Shared.LocalFolder.GitHub/token — no fine-grained token is set for this session; paste one in the GitHub card."
